The fuzzer found a configuration the constructor accepted (supply 1.5e37 units, start price 4.5e64 wei, reserve
1.5e51 wei) in which valuing the supply at the start price overflows, so every bid at that price would fail.
Only absurd parameters are affected; the defaults and the Sepolia sale are many orders of magnitude below.

== 2. Fix (171d16a)
- B1: BidPanel fills the Sell-out amount with formatEthUp(capacity): the room left rounded UP to 6 decimals.
  The bid always sells out and is sent without a minimum; the rounding excess (under 0.000001 ETH) comes back
  in the same transaction with the rest of the surplus.
- B2: the constructor also reverts with InvalidSaleSupply when startPrice > type(uint256).max / saleSupply,
  i.e. when saleSupply * startPrice does not fit in 256 bits. Every ETH amount the auction accepts is at most
  that value divided by 10^18.
  A first version used `(bool fits, ) = Math.tryMul(saleSupply_, startPrice_)`. Slither flagged it:
    DutchAuction.constructor(...) ignores return value by (fits,None) = Math.tryMul(saleSupply_,startPrice_)
    Reference: https://github.com/crytic/slither/wiki/Detector-Documentation#unused-return
    contracts/DutchAuction.sol analyzed (13 contracts with 102 detectors), 16 result(s) found
  unused-return is Medium, so `npm run slither` (--fail-medium) exited non-zero. The division form has no
  ignored value and was committed instead.
- hardhat.config.ts: the unused production compiler profile (500 runs, viaIR) now has the default settings
  (200 runs), so a task that builds with it, such as source verification, reproduces the deployed bytecode.
